## 2. The attribution rule table (`attribution-2026-10-08.1`)

Rules are evaluated in this order; each that applies makes a claim. Claims on one side (ours: OUR_SCOPE, LIKELY_OUR_SCOPE; not ours: RELATED_EXTERNAL, REFERENCE_ONLY) resolve to the first. Claims on both sides resolve to UNKNOWN with every claim kept in `attribution_conflict`, except that the intake association is authoritative (the conflict is still kept). "Related" means the classification's system is one the project has (or any system the rules name, when the project's systems are not known), or a stored title-block discipline that is ours; a discipline that is not ours makes it unrelated.

| Order | Rule | Evidence read | Claim |
|---|---|---|---|
| 1 | intake | the row's intake association (the project's DRF or a Design Sheet) | OUR_SCOPE |
| 2 | originator | `extracted["observations"]` kind `title_block`, key `originator` (no reader stores one today) | this company (`company_name`, `ATTRIBUTION_OWN_ORIGINATORS`): OUR_SCOPE; another: RELATED_EXTERNAL if related, else REFERENCE_ONLY |
| 3 | discipline | the same observation, key `discipline` (none stored today), without an originator | not ours: REFERENCE_ONLY; ours alone: no claim |
| 4 | folder | a folder whose name holds enquiry, enquiries, tender, ifc or issued for construction (`document_control.GIVEN_TO_US`) | RELATED_EXTERNAL if related, else REFERENCE_ONLY |
| 5 | type | outside those folders, stage hint or supported: SHOP_DRAWING | LIKELY_OUR_SCOPE; RELATED_EXTERNAL when the project's DRF says another party draws (`drawings_in_scope` false) |
| 5 | type | IFC_DRAWING outside those folders (a model's answer, for instance) | RELATED_EXTERNAL if related, else REFERENCE_ONLY |
| - | none applies | | UNKNOWN (`rule: no_evidence`) |

OUR_SCOPE comes only from the intake association or a stored originator naming this company; the rules alone never reach it from a type or a folder, so no stage of evidence or model answer grants it (P-10). `drawings_in_scope`, `is_shop_drawing`, roles, registers and the legacy selectors are read, never written.

## 5. Limitations and open items

- Membership (B-19, P-24) is not enforced on the confirmation: the platform has no membership check yet; any design engineer or the design manager may confirm on any project. Estimation engineers are refused; the card's "engineer roles" was read as the design roles plus the design manager.
- No reader stores a title-block originator or discipline (`title_block.TITLE_BLOCK_VERSION` "titleblock-2"); rules 2 and 3 are inert on real data until one does. Attribution on real data today comes from the intake association, the folder and the shop-drawing type.
- Rows written before this change keep `attribution = UNKNOWN` and `attribution_version = NULL` until they are written again (any later processing, sync hint or backfill of a changed row). The backfill's skip test is unchanged, so it does not re-attribute rows whose classification is current; a re-attribution pass is not part of this task.
- `input_fingerprint` is recorded, not compared: a change in the project's systems or `drawings_in_scope` does not mark an attribution stale (freshness semantics were to stay unchanged).
- On SQLite a savepoint opened as a transaction's first statement commits when released (the class of ORCH-038 F-02). `confirm()` writes its audit event first so its savepoint is nested; the automatic writers' behaviour is unchanged.
- `docs/DOCUMENT_CLASSIFICATION_V2.md` still says the confirmation has no endpoint; the frontend types (`ClassificationBasis` has no "engineer"; the new read-model fields are not typed) and the inspector page were not changed. The page shows any basis string as text.
- The AI pass, when ported, should pass `stage_record` (model, prompt version, page characters, job, status) through `record()` rather than mutating `assessment` afterwards (F-02), and its rows will be attributed by the same rules from the type it answers.
