## 1. Migrations schema test
The only difference `compare_metadata` reports is a stray `_alembic_tmp_project_redesign` table left by test 2: the head migration `e6a8c0b2d4f6_drawing_prep_run.py:27` downgrade rebuilds `project_redesign` in batch mode; with this SQLite driver, DDL issued before the first DML in a transaction commits at once, so when test 2 fails the temporary table survives (`alembic_version` rolls back to head), and `reset_database` (tests/conftest.py:90-94) drops only model tables. Alone, the migration chain builds exactly the model schema on SQLite (no missing tables, columns, types or indexes). Startup (`app/main.py:52` → `app/migrations.py:67-103`) backs up when migrations are pending, sets `PRAGMA foreign_keys=OFF`, runs `upgrade head`, restores the pragma; no `create_all`, no ad-hoc ALTERs. The cascade is new with the October migrations (at ed9003e the head's downgrade dropped a model table that `reset_database` cleaned). Notes for M7/M11: SQLite migrations are not atomic with this driver (a mid-way failure leaves committed DDL; the pre-migration backup mitigates); the test compares on SQLite only and proves nothing for PostgreSQL. Fix: fix test 2; optionally have `reset_database` drop `_alembic_tmp_%` tables.

## 2. Archive-model upgrade test
Traceback: `alembic/versions/f2a8c4e01d76_specific_engineer_roles.py:71` batch rebuild of `users` → `DROP TABLE users` → `FOREIGN KEY constraint failed`. The test inserts a Project with `created_by_id` (test line 96) and downgrades on `engine.begin()` (line 101), whose checkout listener turns foreign keys on (`app/database.py:62-67`); SQLite's implicit row deletion on drop then violates `projects.created_by_id`. Production never downgrades (`grep downgrade app/` is empty) and migrates with foreign keys off. Fix (test only, checked in a scratch copy): mirror `app/migrations.py:86-103` by switching `PRAGMA foreign_keys` off around the downgrade/upgrade and back on afterwards; with it, tests 1 and 2 and the other modules give 76 passed, 2 skipped (the remaining failure was test 5).

## 5. Part catalogue test — CODE DEFECT
Assertion at test line 108: the three missing numbers (`3-SDDC2`, `3-SSDC2`, `SIGA-OSD-FCN`) exist only as datasheet file names. `part_catalog.catalog` (`app/services/part_catalog.py:66-131`) never reads the datasheet library: `get_libraries` is imported (:30) but never called, `_from_filename` (:50) has no caller, while the module docstring (:7-8) names the library as the first source. Present since the first commit (09e943d); failed in every recorded Windows run. Effect: `GET /parts/search` (`routers/materials.py:435`) never offers parts known only from datasheet file names, on every deployment. Second divergence: line 118 expects `["CTR160CGL2KS-M"]` but startup seeds `CTR400CGL2KS-M` (`datasheet_links.py:25`, `main.py:62`), a stale expectation. Risk: `DatasheetLibrary.listing()` calls `_refresh()` (datasheet_library.py:311-347), which rescans the library folder after `LIBRARY_RESCAN_SECONDS`; inside `GET /parts/search` that would break the no-work-on-GET rule, so a production fix must read the cached index only (or a background-built catalogue) and match brands with `libraries_for` (:620). Owner question: if dropping the file-name source was deliberate, this becomes a TEST DEFECT and the test and docstring need rewriting.
