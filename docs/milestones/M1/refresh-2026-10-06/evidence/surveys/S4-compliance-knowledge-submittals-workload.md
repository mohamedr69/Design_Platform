### How 'approved as noted' is represented: material submittals versus shop drawings

Material submittals and shop drawings record the same consultant decision in two different ways. On a material submittal revision there is no status for it: the register's four statuses (not_submitted, under_review, approved, rejected) fold the consultant's A and B into 'approved' and C and D into 'rejected', and 'approved as noted' survives only as reply_code 'B' on the submittal, its revision and each history row (models.py:1162, 1211, 1240), shown as the map code ANN (project_state.cell_code@86) and labelled 'Approved as noted' by the page from the code (ProjectMaterialSubmittalPage.tsx:34-43). An engineer cannot enter that code (SubmittalPatch has no reply_code), so a manually approved revision carries no code and reads as A. On a shop drawing revision it is a first-class stored status, approved_as_noted, beside approved, under_review, not_approved and reply_not_found (models.py:2264-2265; shop_drawings.py:50), set by the sync from the reply or by an engineer with confirmed_by_id. Today both views treat it as approved wherever they aggregate: Home takes ANN as an approved code for a system's material (project_state.py:36, 98-110), and the Drawings summary adds approved_as_noted to approved in approved_total (shop_drawings.py:877-883). That is a default nobody recorded, and it is the opposite of the roadmap's rule that approved-as-noted does not count as final until the company records otherwise (section 6). For a workload numerator the two sides are not symmetrical: a shop drawing can be filtered on status == 'approved' alone, but a material submittal needs status == 'approved' and reply_code != 'B', and a manual approval cannot be told from an A. The roadmap's 'one canonical decision set' therefore needs a migration of both: add the distinct value to submittal revisions (with a way for an engineer to set it) and map reply_not_found, not_approved and rejected onto the agreed names.
