## 2. Capability map

The map has 38 rows (C-01 to C-34, with sub-rows). The first group are the ten capabilities the roadmap names; the second group are the further stages the surveys found. Each row appears in two tables that share its ID. Table 2A records identity: where status lives, version or profile, hash or key, idempotency. Table 2B records freshness and reuse: last-good result, stale marking, producer, consumers, and whether another tab reuses the stored result or recomputes it. "none" means the surveys found no such version, key or marker; it is not a guess.

Terms in the reuse column: "stored and reused" means a consumer reads a persisted result; "recomputed on read" means the result is derived again on each request and not stored; "recomputed on read and written" means the GET also writes rows or files; "consumer-local" means one tab holds its own copy and no other tab reads it.

### 5.3 How "approved as noted" is represented

The same consultant decision is stored in two different shapes, and four places read it. This paragraph restates S4 Table E and its explanatory paragraph, with S2 Table B #11.

On a material submittal there is no status for it. The register's four statuses (not_submitted, under_review, approved, rejected) fold the consultant's A and B into approved and C and D into rejected; "approved as noted" survives only as reply code B on the submittal, its revision and each history row (models.py:1162, 1211, 1240), shown as the map code ANN (services/project_state.py:86) and labelled by the page from the code (ProjectMaterialSubmittalPage.tsx:34-43). An engineer cannot enter that code (SubmittalPatch has no reply_code), so a manually approved revision carries no code and reads as A, and a status change does not touch a code read earlier (routers/submittal.py:587-611). On a shop drawing revision it is a first-class stored status, approved_as_noted, set by the sync from the reply or by an engineer with confirmed_by_id. Home treats ANN as an approved code for a system's material (APPROVED_CODES = (A, ANN), services/project_state.py:36, and _state_of at 98-110); for drawings Home maps the Drawings counts as under_review = under_review + reply_not_found, returned = not_approved, and approved only when approved_total equals the floor count (services/project_state.py:216-227), while the Drawings page keeps reply_not_found as its own bucket (shop_drawings.py:883). The Drawings summary adds approved_as_noted to approved in approved_total (services/shop_drawings.py:877-883). Nothing records a company policy: MS.approved_as_noted_policy is NOT_IMPLEMENTED (S4 Table A). Roadmap section 6 says it does not count as final until the company records otherwise; the code does the opposite in Home and in the Drawings summary. For a numerator the two sides differ: a shop drawing can be filtered on status approved alone, but a material submittal needs status approved and reply code other than B, and a manual approval cannot be told from an A. A canonical decision set therefore needs a reviewed migration of both stores (S4 Table E paragraph).

## 7. Limitations

- Static reading only. The surveys ran no code, no test, no endpoint and no database query; no local database exists in the checkout. Every row count, version found in data, and "none locally" statement in the accepted M1 package is UNKNOWN here (S3 section 8 item 1; S1 U-1; S4 U1).
- This document does not re-verify any citation. I copied file:line references from the surveys. The surveys use different abbreviations and I expanded them; a mistake in expansion is possible. Only S5 states that its cited spans were checked against the abstract syntax tree (S5 section 0); the survey files do not say that S1 to S4 were checked mechanically.
- I read S3 Table E, S2 Table E and its constant table, S1 Table E, S4 Table E and the section 7 lists of all five surveys in full. I read Tables A to D of each survey in condensed form (the columns for model location, logic, freshness, missing behaviour and status) and not every cell. A fact that appears only in a Table A cell I did not read could be missing here.
- The surveys disagree on one count. S1 FLR.identity_derivations lists five floor-name readers; S5 C2 row 2 lists seven independent floor-key rules. The difference may be the counting unit; I report both and did not resolve it.
- S2 Table E row 4 says rows with a differing parser_version are "re-read on next processing"; S3 Table B2 says the parser version is consulted only for rows already pending, and nothing makes a row pending. These agree if "next processing" means a processing run that is already scheduled for another reason. I stated the S3 form in V-01 and kept the S2 sentence beside it.
- No reuse or recomputation mark was tested. "Recomputed on read" comes from the surveys' reading of the handler call chains. S5 notes that the Home read, change event and re-read loop may or may not converge in practice; that is UNKNOWN (S5 section 7).
- The roadmap lists "domain projection" as a capability. The surveys do not define it; I mapped it to the stored shop drawing records, the actions and the FA published snapshot because those are the domain records the surveys describe. That mapping is my reading.
- The repository HEAD was 771001e6b70939704a478d09a6740e76778cfecd when this work began and when the surveys were taken. A later `git rev-parse HEAD` during the work returned df185eff1199a7d96181efda6f29e680b6202570. I did not examine what changed; this document describes the surveyed snapshot 771001e.
